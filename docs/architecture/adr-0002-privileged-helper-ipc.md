# ADR-0002: Privileged helper and IPC protocol

- Status: Accepted (design). Implementation is the subject of WP-023 follow-ups; no code exists yet.
  Before the helper gets its first write step, this design needs a human security review
  (see [security architecture](security-architecture.md), rule 2).
- Date: 2026-10-27
- Context packages: WP-023, WP-021 (validation), WP-031 (image write harness)

## Context

WParted plans operations in an unelevated GUI. Executing them needs administrator rights
(`\\.\PhysicalDriveN` write access, volume locks, `IOCTL_DISK_SET_DRIVE_LAYOUT_EX`). Running the whole
GUI elevated would give a large, input-heavy attack surface (file dialogs, drag and drop, rendering,
plan import) full system rights, and every UI bug would become a privileged bug.

Constraints:

- Windows 7 SP1 to Windows 11, x86/x64/ARM64, no installer required (portable ZIP).
- No services and no scheduled tasks: nothing may stay resident or start without the user.
- No telemetry, no network.
- The same core library (parser, validation, serializer) must decide in both processes.

## Decision

### Processes

| Process | Rights | Responsibilities |
|---|---|---|
| `wparted.exe` (GUI) | asInvoker | discovery (read-only), planning, plan export/import, showing progress |
| `wparted-cli.exe` | asInvoker | read-only commands; later `apply --plan` uses the same helper |
| `wparted-helper.exe` | requireAdministrator, started per apply | re-discovery, validation, execution, log |

The helper is started with `ShellExecuteExW` (`lpVerb = "runas"`, `SEE_MASK_NOCLOSEPROCESS`), so
the user sees the UAC consent dialog for every apply. It is never started automatically, has no
"remember" option and exits after one plan. If UAC is disabled or the user is a standard user who
cannot elevate, apply is not available; the GUI says so.

### Channel

- Named pipe `\\.\pipe\WParted-<random 128-bit hex>`; the name is generated by the GUI per apply
  and passed to the helper as its only command-line argument (`--pipe <name>`).
- The **GUI** creates the pipe (`CreateNamedPipeW`, `PIPE_TYPE_MESSAGE | PIPE_READMODE_MESSAGE |
  PIPE_REJECT_REMOTE_CLIENTS`, `FILE_FLAG_FIRST_PIPE_INSTANCE`, one instance) with a DACL that grants
  access only to the interactive user's SID and to `SYSTEM`/`Administrators`. Remote clients and
  further instances are rejected, so another process cannot squat the name or join as a second
  client.
- After `ConnectNamedPipe` the GUI checks `GetNamedPipeClientProcessId` against the PID returned by
  `ShellExecuteExW`. The helper checks `GetNamedPipeServerProcessId` against its parent PID and
  that the server image path equals `wparted.exe`/`wparted-cli.exe` next to its own image.
  Mismatch → the helper exits without doing anything.
- `GetNamedPipeClientProcessId` exists since Windows Vista, so Windows 7 is covered.

### Messages

Each pipe message is one UTF-8 JSON object, limited to 1 MiB and depth 32. The helper parses it
with the strict bounded parser from the core (`parseJson`, same limits). Unknown fields are
rejected rather than ignored.

| Direction | `type` | Content |
|---|---|---|
| GUI → helper | `hello` | `protocol` (integer, currently 1), GUI version |
| helper → GUI | `hello` | `protocol`, helper version; on a mismatch, `error` and exit |
| GUI → helper | `plan` | the plan in exactly the format of *Save plan* (schema `wparted-plan` v1) |
| helper → GUI | `validation` | the helper's own validation result (diagnostics with rule codes) |
| GUI → helper | `confirm` | `planHash` (SHA-256 of the plan text the helper echoed in `validation`) |
| helper → GUI | `progress` | step index, step status, bytes done/total, message |
| GUI → helper | `cancel` | request to stop at the next safe point |
| helper → GUI | `log` | final operation log (`logToJson`, the model from WP-024) |
| helper → GUI | `done` | `result`: `success`, `failed`, `cancelled` |

There are **no** generic commands (no "run program", no paths to executables, no shell strings and
no raw sector writes requested by the GUI). The only input that drives writes is the declarative
plan, and the helper recomputes every sector it writes from the plan and from the disk it reads
itself.

### What the helper does

1. Rediscovers all disks itself and never uses layout data from the GUI.
2. Finds the target disk by plan identity (serial, size, GPT disk GUID / MBR signature) through
   `DiskIdentity::matches`; ambiguity or mismatch → `plan.identity_mismatch`, no writes.
3. Validates with `validatePlan` in execution mode against the layout it just read, plus live state
   (busy volumes, page file, BitLocker, Windows volume, managed-by-Windows disks).
4. Sends the result and waits for `confirm` with the matching hash. The confirmation in the GUI is
   the existing Apply summary, extended by the helper's verdict.
5. Executes step by step. Before each step it re-reads and re-parses the affected area
   (calibration); if that differs from the simulated state of the previous step, it stops.
6. Writes a step journal to `%ProgramData%\WParted\journal\<plan-id>.json` before and after each
   step, so that after a crash or power loss the next start can report which step was interrupted.
   The journal is informational. There is no general rollback, and the documentation says so.

### Cancellation and failure

- `cancel` is honoured only between steps or inside steps that are restartable (block copy in
  chunks). A partition table write is never interrupted.
- If the pipe breaks (GUI crash), the helper finishes the current step, does not start the next
  one, writes the journal and exits.
- If the helper crashes, the GUI shows the last progress and the journal path, and re-runs discovery.

## Alternatives considered

| Option | Why not |
|---|---|
| Run the whole GUI elevated (v0.1 state) | Largest attack surface. Kept only as long as no write path exists. |
| Windows service + RPC | Resident privileged code, needs installation, contradicts the portable ZIP. |
| COM elevation moniker | Needs registry registration (installation); harder on portable media. |
| Helper reads the plan from a file path | TOCTOU on the file, path validation issues; the pipe is simpler and authenticated. |
| Localhost TCP | Network stack, firewall prompts, any local user can connect. |

## Consequences

- One more executable to build, sign and smoke-test; it reuses the core and storage-api libraries.
- The plan format becomes a security boundary: its parser stays strict and fuzzed (random-input and
  limit tests for `parseJson` and mutated-plan import tests already exist in `tests/unit/test_operations.cpp`).
- The read-only guard (`tools/ci/check_readonly.py`) will exempt the helper's writer module only, so
  write APIs stay forbidden in the GUI and CLI.

## Verification plan

- Unit: protocol message parsing (malformed, oversized, unknown fields, wrong order).
- Integration (CI, Wine + images): GUI-less driver runs helper against image files with fault
  injection (pipe closed mid-plan, cancel at every step, identity mismatch).
- Manual gate (maintainer, VM): UAC flow on Windows 7 SP1, 10 and 11, standard user without
  elevation rights, two concurrent instances.
